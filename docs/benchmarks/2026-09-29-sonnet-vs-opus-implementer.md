# Sonnet 5.5 vs Opus 5.5 as the lask implementer（2026-09-29）

## 問的問題

Sonnet 5.5 能不能取代 Opus 5.5 當 `lask:implementer`？實戰配置是 Opus 主 session 派工給 subagent，所以量的是「Opus director＋X implementer」的組合：品質、每題成本、每題時間。

## 做法

- **Repo**：catgame（Unity 6 直式手遊的 .NET 共用規則、MagicOnion 伺服器）。基準 commit `e171ca8`。
- **出題**：Codex gpt-6-astra high。第一輪 4 題是規格明確的工單；第一輪兩邊全滿分後，第二輪 4 題改成只給症狀：三題在程式碼植入 2–3 個互相遮掩的根因（每個根因都有單獨消融驗證，只修一部分會被隱藏測試抓到），一題是要自己定義範圍的產品工單。植入題的起點是沒有 git 歷史的獨立 commit。
- **作答**：每輪一個 `claude -p --model opus --effort high` director，在獨立 worktree 裡把工單原文派給一個 implementer subagent（明確傳 `model`，effort 以 `modelSettings` 固定 high），director 不自己改、不追問。每題每模型 2 次，共 32 輪；另有一波第 3 次重複在開跑 3 分鐘時中止，不計入。
- **客觀驗證**：每輪結束後在該 worktree 跑既有測試（372＋8 skip）＋評審專用隱藏測試。植入題另在未修正的 base 上確認隱藏測試是紅燈。
- **評分**：作答打亂成 A–D，刪除模型名稱，兩位評審各自依 rubric 評 100 分：Codex gpt-6-astra high（read-only）與 `claude -p --model opus --effort xhigh`。
- **越界稽核**：掃描每輪所有工具呼叫，確認沒有讀取原始 repo 或評分包（32 輪全為 0）。

## 解讀

- **規格明確的實作與症狀除錯：打平。** 第二輪的植入根因兩邊都全部找到，連互相遮掩的三因題也一樣；同模型兩次之間的差距和兩模型之間一樣大。
- **開放的產品工單：Opus 較好。** R2-3 是唯一兩位評審方向一致的差距（Opus 97–99、Sonnet 92–95），Opus 在這題花 1.5 倍時間、2 倍成本。
- **成本**：Sonnet 在規格明確的題目約 55–70%；在要自己找根因的題目差距縮小（R2-1 為 86%），因為要多跑幾輪。
- **R2-4 的 49 分**：Astra 對四份都套用 rubric 的「重複扣款」上限，依據是一個靜態推導的反例（時鐘倒退後正常的處理紀錄被誤判成舊格式並淘汰）；另有兩份（一份 Opus、一份 Sonnet）在缺 secrets 時改讀較新版 secrets。兩項都各模型均分，不影響比較。反例的實測結果見下方「R2-4 反例驗證」。
- **評審**：32 份中 28 份兩位評審相差 3 分以內。Opus xhigh 評審每包只花 2–5 分鐘、給分集中在 92–100，沒看到 R2-4 的兩個問題；換成不同模型家族才抓到。

## 限制

- 每格只有 2 次重複；R2-3 的差距方向一致，但 n=2。
- 只測 .NET domain／service；沒有 Unity、UI、美術、Play Mode。
- 兩輪題目兩個模型都解得掉，Sonnet 的上限沒有量到。
- director 固定是 Opus；結論是「Opus 派工給 Sonnet」，不是 Sonnet 單獨運作。
- reviewer、researcher、scout、verifier 沒測。

## 花費

受測 32 輪 $91.2；Opus 評審 $15.7；中止的第 3 波與探測另計約 $3。Astra 出題與評分用 Codex 額度。

## R2-4 反例驗證

用 `lask:implementer`（明確傳 `model: "sonnet"`，transcript 確認為 `claude-sonnet-5-5`，11 分鐘）在四份作答的 worktree 各加同一個測試檔，走真實指令路徑（`HandlerFixture` → `MetaCommandHandler.CatGachaAsync` 寶石單抽 → 磁碟上的 `LocalFilePlayerRepository`，注入 `ManualClock`）：

| 情境 | 四份結果 |
|---|---|
| r000–r510 在時間 T、r511 在 T−1、r512 在 T，之後查 r511 | 四份都已淘汰 r511 |
| 重送 r511 | 四份都重新執行並再扣 150 寶石 |
| 對照：時鐘不倒退 | 四份通過 |
| 同情境但 requestId 用真實客戶端的隨機 GUID | 四份通過 |

所以 Astra 的反例是真的（兩家模型的作答都有，Opus 評審沒看出來），但觸發條件是合成的：要 512 筆 requestId 剛好遞增（循序 ID、手工或舊版依 ID 排序的存檔），再加上一次時鐘倒退。真實客戶端用 `Guid.NewGuid()`，實際上碰不到。這不影響模型比較，但支持「審查交給不同模型家族」這條規則。
